一个 **纯静态、零后端、自动更新** 的中美金融市场牛熊状态展示站。由 **WorkBuddy 本地自动化**（首选）或 GitHub Actions 定时抓取多源免费公开数据，服务端计算牛熊指标后落盘为 JSON，GitHub Pages 仅负责渲染。**全部数据源免密钥**——不需要 `.env`，也不需要配置任何 Secret。

## 架构

```
┌─────────────────┐   定时(cron)    ┌──────────────────────┐   提交 JSON   ┌─────────────────┐
│  GitHub Actions │ ───────────────▶ │  fetch_data.py (服务端) │ ────────────▶ │  data/market.json│
│  (Runner)       │                 │  抓取+牛熊判定+容错     │               └─────────────────┘
└─────────────────┘                 └──────────────────────┘                      │
       ▲                                                                           ▼
       │ 网页推送                                                                 渲染
 免密钥/可选密钥                                                                  ┌─────────────────┐
 数据源：                                                                         │  GitHub Pages   │
 • Yahoo Finance (美股/中债指数)      • 东方财富 push2his (A股)                   │  index.html +   │
 • multpl.com (CAPE / 盈利收益率)     • feargreedchart.com (恐惧贪婪)            │  assets/app.js  │
                                                                                  │  (ECharts)      │
                                                                                  └─────────────────┘
```

**核心约束**：GitHub Pages 是静态托管，浏览器**无法**直连 Yahoo / 东方财富（CORS / 反爬 / 密钥暴露）。
因此所有抓取与判定都在服务端（Actions Runner）完成，前端只渲染已生成的静态 JSON。这是本方案可行的关键前提。

## 部署到 GitHub Pages

本站使用 **GitHub Actions 部署**（仓库 Pages 配置实测为 `build_type: workflow`），由 `.github/workflows/pages.yml` 负责发布。**不要**在 Settings 里选 "Deploy from a branch"——两种模式混用会造成"分支内容即站点"的误解，还会把 88MB 的 `data/history` 一起发布出去。

新仓库首次部署时按此操作：

1. 将仓库推送至 GitHub（公共仓库免费，且 Actions 分钟数不限）。
2. **不需要配置任何 Actions Secret**：所有数据源（Yahoo / 东方财富 / feargreedchart / multpl）均免密钥。
3. **Settings → Pages → Build and deployment → Source 选择 "GitHub Actions"**。
4. 两个工作流的分工：
   - `update.yml`：工作日 21:00 UTC 由 cron 触发抓取与判定，只提交 `data/`；
   - `pages.yml`：发布 `dist/`（由 push 或 `workflow_dispatch` 触发）。
5. 可到 Actions 页手动 `Run workflow` 立即触发。

> **一个容易踩的坑（已修复，2026-10-31 实测）**：用 `GITHUB_TOKEN` 推送的提交**不会**触发其他 workflow（GitHub 的防递归机制）。所以 `update.yml` 提交完数据后，`pages.yml` 的 `on.push` 根本收不到这次提交，**线上会一直停留在上一次部署时的旧数据上**——而 Actions 里两个 run 都显示 success，很难察觉。现在 `update.yml` 末尾显式多跑一步 `gh workflow run pages.yml`（需要 `actions: write` 权限），由它把新数据推上线。

**`pages.yml` 发布的是装配出来的 `dist/`，不是仓库根目录**：只拷贝 `index.html`、`report.html`、`assets/app.js`、`assets/style.css`、`data/market.json`、`data/paradigm.json` 与 `.nojekyll`。因此 `data/history/`（80 余份快照、约 88MB）、`scripts/`、`.github/` 都不会上线——线上访问 `data/history/*.json` 返回 404 属**预期行为**，发布体积从 116MB 降到约 2MB。新增前端文件时，请同步更新 `pages.yml` 的拷贝清单。

> 公共仓库若 **60 天无任何活动**，GitHub 会自动禁用定时任务。`update.yml` 每次运行都会提交数据，
> 只要保持运行即可持续保持活跃，无需额外的 keep-alive 提交。

## 本地自动化（WorkBuddy）

**WorkBuddy 自动化**在本机定时运行 `scripts/fetch_data.py`。全部数据源免密钥，本机与云端行为一致，不存在密钥泄露面。

> 任务定义在 **WorkBuddy 平台侧，不在本仓库内**（`.workbuddy/` 已被 gitignore）。仓库里保留一份可追溯说明：[`automation/local-update.md`](./automation/local-update.md)，记录任务 id、调度、prompt 摘要、双轨关系与重建方法。

1. 平台侧任务 **「牛熊仪表盘-本地数据更新（上午9点）」**（id `automation-1783826526827`），工作日 **09:00 北京时间** 触发，运行 `scripts/fetch_data.py` 并在数据有实质变化时提交推送。
2. 也可在 WorkBuddy 中手动「运行一次」立即刷新。

> **为何两条链路都要**：本机自动化提供人工可介入的入口（可以先看再发），GitHub Actions 提供 24/7 不中断（不依赖本机在线）。两者抓取与判定逻辑完全相同，产物都是 `data/` 下的同一批文件。

## 牛熊判定算法

对每个价格序列计算三类子分后加权（详见 `fetch_data.py`）；并叠加专业维度，最终输出**两条并行的结论**：**加权综合分**（平均多偏）与**共识票数**（几个维度偏）。

**价格序列技术分** `= 0.5·MA排列 + 0.25·RSI(14) + 0.25·MACD(12,26,9)`。

**专业维度（机构级牛熊补充层）**：

| 维度 | 数据源 | 打分逻辑 |
|------|--------|----------|
| 美股 | Yahoo `^GSPC` / `^IXIC`（东财兜底） | 价格序列技术分，标普+纳指等权 |
| A股 | 东财 `push2his`（Yahoo 兜底） | 上证 + 沪深300 + 科创50 + 创业板指，四指数等权 |
| 债券（中美10Y） | Yahoo `^TNX` / 东财 datacenter | **收益率 20 日变化量**：下行 25bp → +1（债牛），上行 → −1 |
| 情绪（恐贪） | feargreedchart | `(FNG-50)/50` |
| 韩股（KOSPI） | Yahoo `^KS11`（东财兜底） | 价格序列技术分；AI 硬件/半导体周期领先指标 |
| 黄金（避险） | Yahoo `GC=F`（东财兜底） | 按金价自身趋势计综合分；避险/实际利率代理 |
| 日元套息 | Yahoo `JPY=X`（东财兜底） | `clamp(USD/JPY 近20日变动 / 5%)`；JPY 弱=套息顺畅=risk-on，JPY 急升=拆仓=risk-off |

> 注 1：**范式相位**（`data/paradigm.json`，佩雷斯框架）为**结构层叠加**，不参与加权；仅通过 `structural_signal` 文字输出参与判读。
>
> 注 2：**量能、波动率、估值、广度四者已全部移出模型**（2026-10-31 第三批修订），不在投票席位、也不作为参考值展示。原因与实测数据见"维度精简"一节。
>
> 注 3：旧的**债券**口径是"对收益率取反后的均线/RSI/MACD"，测的是收益率的**绝对水平方向**。长端收益率长期偏高时它会天天输出负分（历史 80 份快照中该维度从未为正，区间 −0.715~−0.001），等于把期限溢价的结构性上移误读成每日的债市下跌。现改为只看 **20 日变化量**。

**口径 A · 加权综合分（对"实际可用维度"归一化）**：
`0.24·美股 + 0.20·A股 + 0.10·韩股 + 0.14·债券 + 0.08·黄金 + 0.16·情绪 + 0.08·日元套息`（7 项，合计 1.00，运行时仍按可用维度归一化）。
阈值：`≥ +0.33` 牛市，`≤ -0.33` 熊市，之间为震荡。

**口径 B · 共识票数**：每维度 `|分| ≥ 0.15` 才计票，分别数出偏多票与偏空票；`净票数 = 多票 − 空票`，达到 **可用维度数的 1/3（最少 2 票）** 即判多头/空头共识，否则"无共识"。

**为什么要有两条腿**：加权平均在维度高度共线时会正负抵消、恒贴零（历史上情绪↔估值 r = −0.89、美股↔波动率 r = +0.82），阈值 ±0.33 在历史快照中**从未触发**，Hero 大字长期恒定显示"震荡"。共识计数不看强度只看票数，不会被抵消抹平。两者**并列展示**，分歧本身就是信息——"平均偏多但票数不够"意味着多头是少数极端维度撑起来的。

> **维度演进**：13 维 →（移除信用 / 宏观，二者依赖 FRED Key）→ 11 维 →（移除量能 / 波动率）→ 9 维 →（移除估值 / 广度）→ **7 维**。现在 `WEIGHTS` 的每一项都必然可算，"设计维度"与"实际维度"不再存在落差。
>
> 某个维度的数据源本次不可达时（如东方财富代理抖动导致 A股 缺失），该维度仍会自动剔除并重新归一化，避免缺数据导致分数失真。

## 可配置权重面板

仪表盘提供**综合权重配置面板**（`assets/app.js` 渲染，页面"综合权重配置"卡片）：拖动七维度滑块即可按归一化权重实时重算**加权口径与共识口径两套结论**，配置经 `localStorage` 持久化，刷新不丢。权重无需各档之和等于 100（前端会自动归一化）。点"恢复默认权重"即回退到服务端 `present_weights` 默认值。

## 历史快照与失败保护

- **历史快照**：`fetch_data.py` 在成功写出 `market.json` 后，会把它归档一份到 `data/history/YYYY-MM-DD.json`（见脚本「历史快照归档」段），可用于历史回看、回测基线与失败回滚。注意长名日期取 `dt.date.today()`——即**运行环境的本地时区**（GitHub Actions runner 为 UTC，本机运行时为北京时间），两者可能差一天。
- **保留策略**：仓库内只保留最近 **30 天**快照。归档后脚本会自动删除更早的日期文件（`HISTORY_KEEP_DAYS`，默认 30，可用环境变量覆盖，设 0 表示不清理）。每份快照约 1.2MB，不设上限仓库会无限膨胀。
  - 2026-10-31 已做一次性迁移：2026-07-12 ~ 2026-09-30 共 **59 份**移至仓库外 `D:/Coder/_cycleapex-history-archive/`（含 `_MANIFEST.txt` 清单，可用 `cp` 回填），仓库内保留 21 份。
  - ⚠️ 这些文件**仍存在于 git 历史中**：`git rm` 只让 HEAD 变小，**克隆体积不会因此下降**。真要瘦身需改写历史，本项目未做（也无必要——Pages 发布的是装配后的 `dist/`，本就不含 history）。
- **失败保护**：当"可用维度 < 2"时（疑似全源失效），脚本以非零退出码结束且**不覆盖**上一次 `market.json`；同时写入 `data/status.json`（`status: ok / 维度计数`）。
- **自动化告警**：WorkBuddy 自动化任务读取 `status.json`，若 `status != "ok"` 或进程退出码非 0，则保留上一快照并向用户告警，不会"开天窗"或写入空数据。

## 数据更新频率与失败表现

**频率**：本地自动化按**工作日 09:00（北京时间）**触发；云端替代 `update.yml` 为 `0 21 * * 1-5`（UTC，即北京时间次日 05:00）。市场数据为日频，一日一次足够。快照归档由脚本内置完成，云端与本机都会产生。

**为什么"周一没有快照、周六却有"**：这不是漏跑，而是**排期延迟 + 按 UTC 日期命名**叠加的结果。

1. 云端 cron 排期在 **21:00 UTC**，但 GitHub 的定时任务常被延迟数小时才实际执行；
2. 归档文件名取 `dt.date.today()`，在 runner 上是 **UTC 日期**；
3. 一旦延迟跨过 UTC 零点，本来属于"周一 21:00"的那次跑批就会落成"**周二**"的文件名——于是排期里的周一在文件名上消失，而周五那次会落到**周六**。

实测印证（80 份快照全部核对）：**文件名与 `generated_at` 的 UTC 日期 80/80 完全一致**；其中 **20 份**的 `generated_at` 落在 `00:00–03:00 UTC` 区间（即被延迟过零点的跑批）。7 月延迟仅约 50 分钟（如 `21:50Z`），文件名与排期同日；9 月底起延迟普遍超过 3 小时，所以 10 月的每个周一都"缺"了。

**实测覆盖（2026-07-12 → 2026-10-31，迁移前共 80 份快照；仓库内现保留最近 30 天共 21 份，其余 59 份已归档到仓库外）**：

- 6 份落在周末：07-12、07-25、08-29、10-03、10-10、10-31；
- 6 个工作日无快照：08-31、09-28、10-05、10-12、10-19、10-26（**全部是周一**，成因见上）；
- 缺口日没有留下任何降级快照，缺口前后快照的可用维度数也一致（都是 11 维，当时量能/波动率仍在），可佐证是"日期错位"而非"跑批失败"。

**维度覆盖度**：上述 80 份快照全部来自"13 维设计、常态只跑 11 维"的时期——只有 **4 份是 13/13**、**72 份是 11/13**，另有 3 份 10 维、1 份 9 维（早期版本）。缺失的正是依赖 FRED 的**信用**与**宏观**。

> 这段历史落差已通过移除这两个维度消除：`WEIGHTS` 现在共 7 项且全部免密钥，正常情况下首页顶部显示「可用维度 7 / 7」；只有某个源临时不可达时才会出现 6 / 7 之类的数字。

**一次真实失败（2026-07-15）**：脚本退出码 `0`、`status.json` 写 `ok`，但当天 Yahoo 全线 `403`、东方财富连接中断，**实际只有 3/13 维可用**。"可用维度 < 2 才判失败"的守卫没有触发——**这是守卫阈值偏松**：3 维也照样算一次"成功运行"。当天由人工按住不发布（`git checkout -- data/market.json data/status.json` 还原、删除降级快照）等网络恢复。

> 结论：**`status: ok` 只说明脚本没崩，不等于数据完整**。要判断当天数据可不可用，看 `status.json` 里的 `dims_available`。

## 回测一致性校验

`scripts/backtest.py` 复用判定纯函数，对标的做"滚动判定"——在每个交易日用当时可得历史算出牛熊分，再考察其后 N 日前瞻收益，输出各结论态命中率与"分↔前瞻收益"相关系数，验证算法是否含真实信息（而非噪声）。

```bash
python scripts/backtest.py                  # 默认 ^GSPC 近3年，前瞻21日
python scripts/backtest.py --horizon 252    # 前瞻约1年
python scripts/backtest.py --symbol 000300.SS --years 5
python scripts/backtest.py --multi          # 多窗口分段回测（含 2018/2020/2022 回撤；窗口间有重叠），输出 backtest_oos.json
```

> 本地取不到长历史时（Yahoo 对非浏览器来源常年 403，`backtest.py` 会先回退东财长历史，仍失败则退出），可用 `gh workflow run backtest.yml -f horizon=21` 借 GitHub runner 的网络跑一次，结果由工作流自动提交回 `data/backtest_oos.json`。

> 实测（标普500 近 3 年、前瞻 **252 日**、552 个决策点）：牛态标签下 252 日上涨概率 **98.7%**，分数与前瞻收益呈**负相关**（**−0.45**，即 `score_forward_corr=−0.448`），反映动量透支后的中期均值回归——故本分数应作"机制标签"使用，而非独立的短周期择时信号。
>
> **多窗口分段回测（`--multi`，前瞻 21 日）**：覆盖 2014–2019 / 2019–2023 / 2021–2026 三段（含 2018 抛售、2020 新冠崩盘、2022 熊市）。数据源 Yahoo `^GSPC`，区间 2006-10-31 ~ 2026-10-30，重跑于 2026-10-31（`gh workflow run backtest.yml`）。
>
> 后两段有约两年重叠，**同一决策日会被计入两次**，且两次得分并不相同——因为每个窗口只用窗口内历史算均线。所以两个口径都给出：
>
> | 口径 | 决策点 | 牛态命中 | 震荡命中 | 熊态命中 | 分↔前瞻相关 | 全样本平均前瞻 |
> |---|---|---|---|---|---|---|
> | 含窗口重叠 | 3629 | 65.3% | 64.9% | 65.4% | −0.118 | +0.93% |
> | 按决策日去重 | 3026 | 64.6% | 68.2% | 68.5% | −0.152 | +1.02% |
>
> 去重后样本量少 603 个（约 17%）。**去重让负相关变强（−0.118 → −0.152），震荡/熊态命中率上升 3 个百分点左右**，说明重叠样本确实稀释了信号，原先的"轻微负相关"偏保守。两种口径下三档命中率都在 65% 附近，**未显著优于中性基准**；熊态标签前瞻收益为正（含重叠 +2.59%、去重 +3.11%），是典型均值回归特征。故本分数宜作**机制标签**，不宜作独立择时信号。


## 可行性要点

- ✅ **数据源全部免密钥**：Yahoo / 东方财富 / feargreedchart / multpl 均无需 API Key，克隆即可运行，不存在密钥配置与泄露面。
- ⚠️ **非官方 API 有稳定性风险**：Yahoo、东方财富均非官方接口，可能存在限流/临时封禁/字段改版。
  脚本已实现**多源容错**（A 股东财失败回退 Yahoo）、**脏数据防御**（零价 / 未来日期 / 重复日期）、与**指数退避重试**。
- ✅ **静态托管零成本**：GitHub Pages 对公共仓库免费；`data/market.json` 实测 **1.89 MiB**（2026-10-31，含 11 条序列的全量 K 线与指标数组），仍远低于单站 1GB / 月 100GB 带宽限制。
- ✅ **更新频率适配**：所有维度均为日频数据，每个交易日跑一次即可；节奏由两条调度链路统一控制。
- ⚠️ **中债10Y**：走东方财富 datacenter（best-effort，失败则债券维度仅用美债10Y，不影响其余维度）。
- ⚠️ **已放弃的能力（真实损失）**：信用利差（HY OAS）、宏观（CPI/失业率/GDP）、10Y-2Y 曲线、实际利率——这些都只能从 FRED 取，随密钥依赖一并移除。换来的是零密钥与"每一项权重都必然可算"。

## 维度精简：13 → 7 维的完整依据（2026-10-31 三批修订）

不是拍脑袋，是在 80 份历史快照（2026-07-12 ~ 10-31）上做 leave-one-out、共线性诊断与事件研究后删的。三批各自独立，每批都能拿出数据。

**第一批：信用 / 宏观（13 → 11）**——依赖 FRED API Key。本项目明确不使用任何密钥数据源，所以这两维是「做不了」，不是「做不好」。不是降级为待配置，是代码与权重一并删除。

**第二批：量能 / 波动率（11 → 9）**——能算，但算出来的东西没用。

| 维度 | 权重(旧) | σ | 自然节奏 | 与综合分 r | 判定 |
|---|---|---|---|---|---|
| 量能 | 0.07 | 0.180 | 平均 **1.8 天**翻一次，79 天翻 42 次 | −0.12 | 噪声 |
| 波动率 | 0.06 | 0.068 | 平均 26 天 | +0.68 | VIX 与美股 r=+0.82，纯复述 |

量能还有一处更深的问题：`价跌放量=派发` 这组后续 21 日收益是 **+1.42%（上涨概率 100%）**，与"派发"的符号假设正好相反——放量下跌更像是恐慌出清而不是机构出货。

**第三批：估值 / 广度（9 → 7）**——这两项属于「名不副实」，比噪声更麻烦。

| 维度 | 名义测什么 | 实际测什么 | 证据 |
|---|---|---|---|
| 估值 | CAPE / ERP | **价格距 200 日均线的偏离度** | 真实 CAPE 命中 **0/80**、ERP 命中 0/80；兜底代理与 20 日动量 r=**+0.65** |
| 广度 | A股涨跌家数 + 美股等权/市值 | **单一美股小盘-大盘风格差** | A股侧命中 **0/80**，「跨市场复合」从未生效 |

估值还有一个隐蔽危害：它的偏离度只在 +3.7%~+8.8% 间波动，导致该维度**常年输出 −0.15~−0.35 的负分**，是个结构上只会投空票的伪维度。实测它制造了 **12 次虚假空头共识**——把它移出后，80 份快照的共识分布从「多 0 / 无 48 / 空 32」变成「多 5 / 无 55 / 空 20」。

**第三批的效果**（同批 80 份快照）：

| 方案 | 维度数 | 综合分 σ | 共识触发率 | r(标普未来21日) |
|---|---|---|---|---|
| 原 11 维加权 | 11 | 0.051 | — | — |
| 9 维加权（含假估值） | 9 | 0.084 | 40% | −0.561 |
| 全部维度不变、改共识计数 | 11 | 0.139 | 52% | — |
| **现 7 维加权** | 7 | **0.097** | 31% | −0.571 |

两条主线：**删维度能把 σ 从 0.051 抬到 0.097（+90%），换聚合方式能把触发率从 0% 抬到 52%**。两者解决的是不同问题，所以都做了。

> **KOSPI 保留**：专项考察过。覆盖 79/80、σ=0.324（信息量充足）、与综合分 r=+0.435；虽与已删的广度 r=−0.62 有重复，但删掉后综合分 σ 反而降 2.4%，leave-one-out 判定"影响中性"。
>
> **已知局限（必须说清）**：80 份快照全在 2026-07~10 的单边上涨行情里。所有方案的加权分与未来 21 日收益都是**负相关**（−0.41 ~ −0.58），说明它在样本内是反向指标，**不能当择时工具**，只能当状态描述/风险温度计。跨市场长历史回测仍是待办。

## 周末与休市的数据容错

休市不是异常，是常态（一年约 1/4 的日子）。之前只报 `generated_at`，会让读者以为周末也有新数据，而且同一根 K 线会被重复归档进历史。

现在分开两个概念：

- **`generated_at`** = 脚本什么时候跑的
- **`data_freshness.as_of`** = 数据实际截止到哪天（取各市场最新 K 线的最大日期）

页面顶部优先显示**数据截止日**，并配一个状态徽章：

| 状态 | 触发条件 | 含义 |
|---|---|---|
| `live` | 今天是工作日，且缺失工作日 ≤ 1 | 数据是最新可得 |
| `market_closed` | 今天是周末，或缺失 2~3 个工作日 | 正常休市，数据为最近交易日收盘 |
| `stale` | 缺失 ≥ 4 个工作日 | 长假或数据源异常，需要人工核对 |

判定用**「缺失工作日数」而不是自然日差**：周一盘前跑，数据是上周五的，自然日差 3 天看起来像"停了三天"，但中间只隔 1 个工作日（周一当天还没收盘），属于完全正常。不维护中美节假日表——两边节日各十来天且每年变动，维护成本远大于收益，长假会被缺工作日数自然放大（国庆 7 天 ≈ 5 个工作日），足以触发 `stale`。

**跨市场不同步**单独处理：如果 A 股因长假停在 9/30、美股已到 10/7，`skew_days = 7` 会写进 payload，页面 Hero 区弹出提示——因为这时"综合分"混用了不同日期的数据，不标出来就是误导。

另外加了三层脏数据防御（`build_series`）：

1. **零价/负价**直接丢弃——部分源在休市或异常时用 0 占位，0 会让收益率变形并污染均线、RSI；
2. **未来日期**丢弃——时区错乱时会吐出明天/后天的点，会把"数据截止日"算到未来，让新鲜度判断失效；
3. **乱序与重复**按日期升序去重，保证"最后一根 = 最新交易日"这个假设成立。

历史快照归档也做了去重：如果 `as_of` 与上一份快照相同（没有新数据），不再新增文件，而是原地覆盖——避免同一根 K 线被重复计入回测基线。
